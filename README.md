# репозиторий по АИС
Введение
REST API является фундаментальным компонентом современных распределённых систем, обеспечивая взаимодействие между сервисами, клиентскими приложениями и внешними интеграциями. Производительность API напрямую влияет на пользовательский опыт, масштабируемость системы и её способность выдерживать реальные нагрузки. Поэтому тестирование производительности REST API — обязательный этап обеспечения качества.
 
1. Виды тестирования производительности REST API
1.1. Нагрузочное тестирование
Нагрузочное тестирование (Load Testing) — это проверка работы API при нагрузке, которая считается нормальной или близкой к ожидаемой в реальной эксплуатации. Его задача — не «сломать» систему, а убедиться, что она уверенно работает в пределах проектных значений.
1)	Что обычно проверяют:
•	стабильность времени отклика при росте числа запросов;
•	способность API выдерживать длительную нагрузку без деградации;
•	корректность работы под типичным трафиком (например, 500 RPS в течение часа);
•	соответствие SLA, если оно определено.
2)	Типичные проблемы, которые выявляет нагрузочное тестирование:
•	постепенное увеличение времени отклика (эффект «ползущей деградации»);
•	утечки памяти;
•	рост очередей в базе данных;
•	неэффективные запросы, которые проявляются только под нагрузкой.
3)	Пример практического сценария:
API интернет-магазина должен выдерживать 2000 запросов в минуту в течение рабочего дня. Нагрузочный тест имитирует такой трафик, чтобы убедиться, что система не «проседает» к концу дня.
1.2. Стрессовое тестирование
Стрессовое тестирование (Stress Testing) направлено на то, чтобы определить пределы системы. В отличие от нагрузочного тестирования, здесь нагрузка намеренно превышает нормальные значения — иногда в несколько раз.
1)	Цели стресс-тестирования:
•	найти точку отказа API;
•	понять, как система ведёт себя при перегрузке;
•	проверить способность к восстановлению после отказа;
•	выявить узкие места, которые не проявляются при обычной нагрузке.
2)	Что важно в стресс-тестах:
•	не только момент отказа, но и поведение после него;
•	корректность обработки ошибок (например, возврат 503 вместо зависания);
•	способность API вернуться в рабочее состояние без ручного вмешательства.
3)	Пример:
Если API рассчитан на 1000 RPS, стресс-тест может постепенно довести нагрузку до 5000 RPS, чтобы увидеть, где именно начинаются ошибки и как быстро система восстанавливается.
1.3. Объёмное тестирование
Объёмное тестирование (Volume Testing) проверяет не количество запросов, а объём данных, которые API должен обработать. Это особенно важно для систем, работающих с большими JSON-структурами, файлами, массивами или большими выборками из БД.
1)	Что проверяют:
•	время обработки больших payload;
•	влияние размера данных на время отклика;
•	устойчивость к большим ответам (например, 10 МБ JSON);
•	корректность работы при больших объёмах данных в базе.
2)	Типичные проблемы:
•	переполнение памяти при сериализации больших объектов;
•	медленные запросы к базе данных;
•	увеличение времени GC (сборки мусора);
•	ошибки при обработке больших файлов.
3)	Пример:
API аналитической системы должен возвращать отчёты размером до 20 МБ. Объёмный тест проверяет, как API ведёт себя при таких данных и не приводит ли это к перегрузке сервера. 
2. Метрики производительности REST API
Метрики — это основа анализа результатов тестирования. Без них невозможно объективно оценить, насколько API справляется с нагрузкой.
Ниже приведены ключевые метрики, которые используются в инженерной практике.
2.1. Время отклика (Response Time)
Это одна из главных метрик. Она показывает, сколько времени проходит между отправкой запроса и получением ответа.
Варианты измерений:
•	среднее время отклика — полезно, но может скрывать пики;
•	медиана — более устойчива к выбросам;
•	95-й и 99-й перцентили — показывают, как ведут себя «медленные» запросы;
•	максимальное время отклика — важно для SLA.
Почему перцентили важнее среднего:
Среднее может быть 50 мс, но если 5% запросов отвечают 2 секунды, пользователи будут недовольны.
2.2. Пропускная способность (Throughput)
Показывает, сколько запросов API способен обработать за единицу времени (обычно RPS — requests per second).
Что важно:
•	пропускная способность под нагрузкой;
•	стабильность RPS при росте нагрузки;
•	зависимость RPS от размера данных.
2.3. Уровень ошибок (Error Rate)
Процент запросов, завершившихся ошибкой (4xx, 5xx).
Что анализируют:
•	рост ошибок при увеличении нагрузки;
•	типы ошибок (например, 500 — проблемы сервера, 429 — лимиты);
•	корреляцию ошибок с временем отклика.
2.4. Использование ресурсов (CPU / Memory / Disk / Network)
Нагрузочные тесты всегда сопровождаются мониторингом ресурсов.
Что важно:
•	пики CPU при сериализации JSON;
•	рост памяти при больших объёмах данных;
•	задержки диска при работе с БД;
•	сетевые задержки при больших ответах.
2.5. Latency (задержка)
Latency — это время, которое запрос проводит в очереди до начала обработки. Особенно важно для систем с балансировщиками, очередями и API Gateway.
2.6. Concurrency (число одновременных соединений)
Показывает, сколько клиентов API может обслуживать одновременно без деградации.
 
Заключение
Тестирование производительности REST API — это не разовая процедура, а постоянная инженерная практика. Нагрузочные тесты позволяют убедиться, что система выдерживает ожидаемый трафик. Стрессовые тесты показывают пределы и помогают подготовиться к пиковым ситуациям. Объёмные тесты выявляют проблемы, связанные с большими данными.
Использование метрик — от времени отклика до уровня ошибок и использования ресурсов — позволяет объективно оценивать состояние системы и принимать инженерные решения на основе данных.
